## A — Graphe source réel et provenance des phases

```text
WbSimulationWorld::step [principal / appel ordinaire]
  ├─ plugin.step()                      [AVANT physique, code plugin arbitraire]
  └─ WbSimulationCluster::step()
      └─ dWorldStepAndSpaceCollide
          ├─ MT disabled : dWorldStep puis callback dSpaceCollide [appelant]
          └─ MT enabled :
              ├─ clusterManager->simLoop
              ├─ threadManager->simLoop
              │   ├─ appelant -> BARRIER1 -> attend BARRIER2
              │   └─ workers pthread 0..n-1
              │       -> BARRIER1
              │       -> simLoopChild:
              │           clusterLCP (solver)
              │           odeSensorRaysUpdate (optionnel)
              │           clusterCollide -> dSpaceCollide
              │              -> odeNearCallback
              │                 -> plugin.collide()             [hors M]
              │                 -> M.lock -> dJointCreateContact
              │                              -> dJointAttach -> M.unlock
              │       -> BARRIER2
              └─ heuristicsManager->simLoop
      [dWorldStepAndSpaceCollide retourné, et NON simplement BARRIER2]
      ├─ swapBuffer / handleKinematicsCollisions
      ├─ dJointGroupEmpty(pluginContactJointGroup)
      ├─ emptyEnabledBodyContactJointGroups(back buffer)
      └─ dImmersionLinkGroupEmpty
  └─ plugin.stepEnd()                  [APRÈS physique]
```

Le passage `MT disabled` ci-dessus reflète l'ordre effectif **solver puis collision**
du `dWorldStepAndSpaceCollide` épinglé, qui n'est pas l'ordre de l'API distincte
`dSpaceCollideAndWorldStep`. L'observation native doit distinguer les deux.

**Écart capital 1 worker** : `WbOdeContext::setNumberOfThreads(1)`
appelle expressément `dToggleODE_MT(0)`; il y a zéro worker ODE, même si
`optimalThreadCount=1`. La fixture « 1 worker » force, **uniquement par
instrumentation isolée**, `dToggleODE_MT(1)`. Deux threads configurés ne
prouvent pas deux threads exécutant le callback ; l'oracle exige deux TID
distincts à l'intérieur de `worker_task_enter ... plugin_callback ... exit`.

**Écart de frontière** : le retour de `threadManager->simLoop()` prouve que
les workers qui ont traversé BARRIER2 ont fini le travail de cette boucle.
Le retour de `dWorldStepAndSpaceCollide` inclut en plus
`heuristicsManager->simLoop`. Ni cette barrière ni ce retour n'établissent
l'arrêt d'éventuels threads privés d'un plugin ou d'un second appel concurrent
hors du scheduler. Une quiescence globale Φ ne découle PAS du seul code.

## B — Graphe des attentes et risques de deadlock

```text
B1  Webots détient M -> ODE destruction -> hook dJointDestroy -> attend M
    M --> M                                    [auto-deadlock si hook réentrant]

B2  worker W dans odeNearCallback -> plugin.dJointDestroy -> attend Φ
    Φ attend BARRIER2, BARRIER2 attend W       [cycle W -> Φ -> W]

B3  thread X possède M et attend Φ/worker W
    W (contact create ou P0 admission) attend M
    X -> W -> M -> X                           [inversion de hiérarchie]

B4  thread X libère le joint J sous M; solver W utilise encore J
    M n'est PAS une exclusion des lectures ODE; une absence de deadlock
    est compatible avec un UAF.

B5  plugin.cleanup -> threads privés non joints; destruction corps / cluster
    / monde -> libération J, threads privés -> J
    Un ordre d'appel séquentiel n'est PAS un join de threads plugin.
```

- **B1 possible sous hook naïf** : `WbOdeContext::removeBodyContactJointGroup`
  verrouille le QMutex avant la destruction des groupes. Le candidat standalone
  #766 verrouille aussi le retrait de tampon et le RESET. Une interception ODE
  qui reprend M sur destruction interne crée une réentrance. Le remède
  *conceptuel* est un chemin interne explicite `destroyOwnedContactLocked`
  sans repasser par l'admission publique ; **non implémenté ici**.
- **B2 contre-exemple d'architecture**, si un plugin attend Φ depuis un
  callback worker : ce worker est lui-même participant à la barrière. Un
  refus P0 *immédiat*, après classification LIVE sous M et sans attendre Φ,
  évite cet auto-cycle, mais ne suffit pas à prouver la durée de vie lors
  de l'admission, ni la sûreté des joints plugin détruits effectivement.
- **B3 impossible seulement sous discipline à démontrer** : ne jamais
  prendre M avant d'attendre la fin du scheduler, et interdire callbacks
  arbitraires depuis le nettoyage sous M. Aucune preuve de hiérarchie des
  mutex propres aux plugins n'est contenue dans le code Webots.
- **B4** : retrait du groupe plugin puis du tampon se situe après le retour
  de l'appel ODE normal ; c'est un **point candidat** de quiescence des workers
  de ce pas, pas une preuve de sûreté d'autres utilisateurs de J.
- **B5 source exacte** : `WbSimulationWorld::~` appelle
  `delete mPhysicsPlugin` (donc son `webots_physics_cleanup`) AVANT
  `root()->deleteAllChildren()`, puis `delete mCluster`, puis
  `delete mOdeContext`. Le contexte détruit les deux groupes moteur
  et les deux groupes plugin, puis `dSpaceDestroy`, `dWorldDestroy`.
  La conformité de threads créés par le plugin est hors garantie de
  cet ordre. `dJointGroupEmpty` et `dWorldDestroy_ST` libèrent sans
  repasser par le point public `dJointDestroy` :
  [ode.cpp L1252-1315 et L1539-1584](https://github.com/cyberbotics/webots/blob/c6793d8f7230a311c4bc2a3101d9f1a8bc0aa01b/src/ode/ode/src/ode.cpp#L1252-L1315).

## Contrat minimal **à tester**, non présupposé

`M` = même QMutex **non récursif** pour décision P0, double registre LIVE,
désinscription et destruction interne explicite ; aucun appel externe plugin
sous M. `Φ` = quiescence de tous utilisateurs susceptibles de lire le joint,
dont solver/workers, et éventuellement threads plugin sous un contrat séparé.
Ordre des destructions moteur **Φ puis M**. Pendant un callback worker,
le `dJointDestroy` public sur contact moteur LIVE doit retourner **sans attendre
Φ**, après seule classification sûre sous M. L'accès au registre et la durée de vie
du joint doivent déjà être couverts par un contrat d'entrée H0 ; deux tentatives
sur identifiant détruit sont hors domaine. Aucune tombstone ABA ni
autorisation par identité du thread.

Les contacts plugin standalone gardent la destruction ODE normale ; contacts
plugin group-owned gardent le no-op de `dJointDestroy` et la destruction par
`dJointGroupEmpty`. L'origine « Webots » ne peut pas être déduite du TID.
Cette branche ne teste **aucune** implémentation du contrat : un résultat
positif de la baseline group-owned ne peut pas justifier P0 sur standalone.
